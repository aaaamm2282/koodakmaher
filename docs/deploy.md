# انتشار سایت روی هاست

سایت «ایستا» است: دستور `npm run build` همه‌ی صفحه‌ها را یک بار می‌سازد و در پوشه‌ی `dist` می‌گذارد. روی هاست فقط همین پوشه لازم است؛ نه پایگاه داده دارد و نه برنامه‌ای که با هر بازدید اجرا شود. به همین دلیل سریع است و چیزی برای هک شدن ندارد (به‌جز گیرنده‌ی فرم‌ها که جداگانه و کوچک است).

این راهنما چهار کار را توضیح می‌دهد: انتخاب هاست، انتشار خودکار از GitHub، بارگذاری دستی، و بررسی خودکار کیفیت. برای جابه‌جایی از وردپرس (ریدایرکت‌ها و روز راه‌اندازی) راهنمای [migration.md](migration.md) و برای فرم‌ها [forms-setup.md](forms-setup.md) را ببینید.

## ۱. کدام هاست؟

| | هاست اشتراکی ایرانی (cPanel یا DirectAdmin) | Netlify یا Cloudflare Pages | سرور مجازی با nginx |
|---|---|---|---|
| ریدایرکت‌ها، صفحه‌ی ۴۰۴، فشرده‌سازی و کش | خودکار، با فایل `.htaccess` همراه سایت | خودکار، با `_redirects` و `_headers` | خروجی `npm run migrate:nginx` در تنظیمات nginx |
| فرم‌ها (گیرنده‌ی PHP) | بله | نه؛ فرم‌ها باید به نشانی دیگری فرستاده شوند | بله، با PHP-FPM |
| انتشار خودکار | GitHub Actions با FTP (بخش ۳) | خود میزبان با هر تغییر می‌سازد؛ ساخت روزانه با build hook (بخش ۵) | دستی یا با rsync |

**پیشنهاد:** هاست اشتراکی ایرانی با Apache یا LiteSpeed، PHP 8 (با افزونه‌ی `intl` برای تاریخ شمسی در فایل فرم‌ها)، گواهی SSL رایگان (AutoSSL یا Let's Encrypt) و FTP با رمزنگاری (FTPS). پیش از خرید از پشتیبانی هاست این سه را بپرسید:

1. آیا سایت از **خارج از ایران** باز می‌شود؟ گوگل سایت‌ها را از خارج از ایران می‌خواند؛ هاستی که دسترسی خارجی را می‌بندد، سایت را از نتایج گوگل بیرون می‌اندازد.
2. آیا **FTP از خارج از ایران** وصل می‌شود؟ انتشار خودکار از سرورهای GitHub انجام می‌شود. اگر نه، از روش «zip» در بخش ۳ استفاده کنید.
3. آیا `AllowOverride` برای `.htaccess` دست‌کم `FileInfo` است؟ (در تقریباً همه‌ی هاست‌های cPanel همین‌طور است.)

## ۲. تنظیمات ساخت

این مقدارها هنگام ساخت در سایت نوشته می‌شوند. هیچ‌کدام رمز نیست، چون همه در HTML سایت دیده می‌شوند.

| نام | مقدار | توضیح |
|---|---|---|
| `SITE_URL` | `https://mahermana.com` | نشانی نهایی سایت؛ برای canonical، نقشه‌ی سایت و کد QR. خالی بماند همین مقدار است. |
| `PUBLIC_FORM_ENDPOINT` | `/api/form.php` | مقصد فرم‌ها ([forms-setup.md](forms-setup.md)). خالی بماند، فرم‌ها چیزی نمی‌فرستند. |
| `PUBLIC_GA4_ID`، `PUBLIC_UMAMI_SRC`، `PUBLIC_UMAMI_ID` | | آمار بازدید (اختیاری؛ همان راهنما). |

کجا نوشته شوند:

- **روی کامپیوتر خودتان:** فایل `.env` (نمونه با توضیح: `.env.example`).
- **انتشار خودکار از GitHub:** مخزن ← **Settings** ← **Secrets and variables** ← **Actions** ← زبانه‌ی **Variables** ← **New repository variable**.
- **Netlify یا Cloudflare Pages:** بخش Environment variables در تنظیمات همان سایت.

`SHOW_DRAFTS` و `PREVIEW_PHOTOS` فقط برای بازبینی روی کامپیوتر خودتان است و هرگز در نسخه‌ی اصلی تنظیم نشود (همه‌ی صفحه‌ها `noindex` می‌شوند؛ ابزار انتشار چنین نسخه‌ای را بارگذاری نمی‌کند). `STATIC_REDIRECT_PAGES=1` فقط برای هاستی است که هیچ ریدایرکتی نمی‌پذیرد ([migration.md](migration.md)، بخش هاست‌ها).

نسخه‌ی Node در فایل `.nvmrc` است (`22.23.4`؛ Astro 7 با نسخه‌ی قدیمی‌تر اجرا نمی‌شود). GitHub، Netlify و Cloudflare همین را می‌خوانند.

## ۳. انتشار خودکار روی هاست اشتراکی (GitHub Actions)

گردش کار `.github/workflows/deploy.yml` (در زبانه‌ی Actions با نام **Deploy**) این کارها را می‌کند:

- **بعد از هر تغییر در شاخه‌ی `main`**، از جمله هر «انتشار» در پنل مدیریت: سایت را می‌سازد، روی هاست بارگذاری می‌کند و سایت زنده را بررسی می‌کند. حدود ۳ تا ۵ دقیقه طول می‌کشد.
- **هر روز ساعت ۴ صبح به وقت تهران:** اگر تاریخ انتشار مقاله یا اطلاعیه‌ای رسیده باشد، دوباره می‌سازد تا آن مطلب منتشر شود. روزهای دیگر کاری نمی‌کند.
- **با دکمه:** Actions ← Deploy ← **Run workflow**.

اگر ساخت به خطا بخورد (مثلاً ریدایرکت اشتباهی در پنل وارد شده باشد)، چیزی بارگذاری نمی‌شود و سایت فعلی دست نمی‌خورد. GitHub برای اجرای ناموفق به صاحب مخزن ایمیل می‌زند.

### یک بار، برای راه‌اندازی

**۱. شاخه‌ی اصلی مخزن را `main` کنید.** مخزن ← Settings ← General ← **Default branch** ← `main`. پنل مدیریت در `main` می‌نویسد و اجرای روزانه‌ی GitHub از شاخه‌ی پیش‌فرض خوانده می‌شود.

**۲. یک حساب FTP جدا بسازید.** cPanel ← **FTP Accounts** ← یک نام (مثل `deploy`)، رمز قوی و Directory برابر `public_html`. حساب جدا یعنی اگر روزی رمزش لو برود، فقط به پوشه‌ی سایت دسترسی دارد و می‌شود بدون دست زدن به حساب اصلی عوضش کرد. در DirectAdmin: **FTP Management** ← Create FTP Account.

در همان صفحه، **Configure FTP Client** کنار حساب، نشانی سرور (FTP server) و درگاه (معمولاً ۲۱) را نشان می‌دهد.

**۳. رمزها و تنظیم‌ها را در GitHub بنویسید.** مخزن ← Settings ← Secrets and variables ← Actions.

زبانه‌ی **Secrets** (فقط GitHub می‌بیند؛ در گزارش اجرا هم با `***` پوشانده می‌شود):

| نام | مقدار |
|---|---|
| `FTP_HOST` | نشانی سرور FTP، مثل `ftp.mahermana.com` یا نام سروری که Configure FTP Client نشان می‌دهد |
| `FTP_USER` | نام کاربری کامل حساب FTP، مثل `deploy@mahermana.com` |
| `FTP_PASSWORD` | رمز همان حساب |

زبانه‌ی **Variables**:

| نام | مقدار | کی لازم است |
|---|---|---|
| `DEPLOY_TARGET` | `ftp` | همیشه؛ تا خالی است، انتشار خودکار خاموش است |
| `SITE_URL`، `PUBLIC_FORM_ENDPOINT` و بقیه‌ی بخش ۲ | | همان‌طور که در بخش ۲ آمده |
| `FTP_DIR` | `.` | وقتی حساب FTP مستقیم در `public_html` باز می‌شود (حساب جدای مرحله‌ی ۲). پیش‌فرض `public_html` است که برای حساب اصلی cPanel درست است. |
| `FTP_PROTOCOL` | `sftp` یا `ftp` | پیش‌فرض `ftps` است (FTP رمزنگاری‌شده). `ftp` بدون رمزنگاری است و فقط اگر هاست هیچ راه دیگری ندارد. |
| `FTP_PORT` | | فقط اگر هاست درگاه دیگری داده است |
| `FTP_VERIFY_CERTIFICATE` | `no` | فقط اگر خطای گواهی آمد و نشانی دیگری از هاست کمکی نکرد (بخش ۷) |
| `SFTP_KNOWN_HOSTS` | خروجی `ssh-keyscan نشانی-سرور` | با `sftp`، تا کلید سرور بررسی شود |
| `FTP_DELETE` | `true` | فایل‌هایی را که دیگر جزو سایت نیستند (مثلاً مقاله‌ی حذف‌شده) از هاست پاک می‌کند. بعد از اولین بارگذاری موفق روشن کنید. پوشه‌های خود هاست (`.well-known`، `cgi-bin`، `.user.ini`، `php.ini`، `error_log`) هرگز پاک نمی‌شوند. |
| `DEPLOY_CHECK` | `off` | بررسی سایت زنده بعد از بارگذاری را خاموش می‌کند؛ فقط تا وقتی دامنه هنوز به هاست تازه اشاره نمی‌کند |

هر فایلی که باید در ریشه‌ی سایت باشد (مثل فایل تأیید یک سرویس) را در پوشه‌ی `public/` مخزن بگذارید، نه مستقیم روی هاست؛ این‌طوری با هر انتشار همراه سایت می‌رود و با `FTP_DELETE` هم پاک نمی‌شود.

### روز اول: پیش از اولین بارگذاری

1. از وردپرس **پشتیبان کامل** بگیرید ([migration.md](migration.md)، «پیش از راه‌اندازی»).
2. **فایل‌های وردپرس را از `public_html` بیرون ببرید.** File Manager ← Settings ← Show Hidden Files را روشن کنید. در پوشه‌ی خانه (Home، بالای `public_html`) با **+ Folder** پوشه‌ی `wordpress-old` را بسازید. بعد در `public_html` همه را انتخاب کنید به‌جز `.well-known` و `cgi-bin` ← **Move** ← مسیر `/wordpress-old`. اگر بمانند، فایل‌هایی مثل `wp-login.php`، `xmlrpc.php` و افزونه‌های قدیمی همچنان اجرا می‌شوند و راه نفوذند، و در بعضی هاست‌ها `index.php` وردپرس به‌جای صفحه‌ی اصلی تازه باز می‌شود. پایگاه داده‌ی وردپرس را لازم نیست پاک کنید.
3. Actions ← Deploy ← **Run workflow**. گام‌ها را در گزارش اجرا دنبال کنید. گام آخر سایت زنده را بررسی می‌کند (همان `npm run migrate:check` در migration.md) و باید سبز شود.
4. بقیه‌ی کارهای روز راه‌اندازی (سرچ کنسول، نقشه‌ی سایت، Bing): [migration.md](migration.md)، «روز راه‌اندازی».

### ترتیب بارگذاری

اسکریپت `scripts/deploy-ftp.sh` طوری بارگذاری می‌کند که سایت زنده در میانه‌ی کار خراب دیده نشود:

1. فایل‌های تازه‌ی `_astro/` (CSS و JavaScript و فونت‌ها). نام این فایل‌ها با محتوایشان عوض می‌شود، پس فایل‌های قبلی سر جایشان می‌مانند و صفحه‌ای که باز است خراب نمی‌شود.
2. صفحه‌ها، عکس‌ها و `.htaccess`. هر فایل اول با نام موقت بارگذاری و بعد جایگزین می‌شود، تا بازدیدکننده هیچ‌وقت نیمه‌ی یک صفحه را نبیند.
3. فایل‌های قدیمی `_astro/` که دیگر هیچ صفحه‌ای از آن‌ها استفاده نمی‌کند پاک می‌شوند.

### اگر GitHub به هاست وصل نشد

خطای `max-retries exceeded` یا `Connection timed out` در گام Upload یعنی هاست اتصال از خارج از ایران را بسته است (گاهی موقت، در اختلال‌های اینترنت). دو راه دارید:

- از هاست بخواهید FTP از خارج را باز کند.
- `DEPLOY_TARGET` را `zip` کنید. سایت ساخته می‌شود ولی بارگذاری نمی‌شود؛ پایین صفحه‌ی همان اجرا، در بخش **Artifacts**، فایل `site-…` را بگیرید و مثل بخش ۴ بارگذاری کنید. (در حالت `ftp` هم همین فایل همیشه هست، پس اگر بارگذاری یک بار شکست خورد، می‌شود دستی بارگذاری کرد.)

اگر خود سایت هم از خارج باز نمی‌شود، گوگل هم آن را نمی‌بیند. این را حتماً با هاست حل کنید.

### اجرای روزانه در مخزن عمومی

این مخزن عمومی است. GitHub در مخزن عمومی‌ای که ۶۰ روز هیچ تغییری نداشته باشد، اجراهای زمان‌بندی‌شده را خاموش می‌کند. نشانه‌اش: مقاله‌ی زمان‌بندی‌شده سر تاریخش منتشر نمی‌شود. Actions ← Deploy ← **Enable workflow**، و همان‌جا یک بار Run workflow. انتشار هر مطلبی از پنل مدیریت هم این شمارش را از نو شروع می‌کند.

## ۴. بارگذاری دستی

**بدون خط فرمان (File Manager):**

1. فایل آماده را از GitHub بگیرید (بخش ۳، Artifacts) یا روی کامپیوتر خودتان `npm ci` و `npm run build` را اجرا کنید و **محتوای** پوشه‌ی `dist` (نه خود پوشه) را zip کنید.
2. cPanel ← File Manager ← `public_html` ← **Upload** ← فایل zip ← بعد از بارگذاری، روی آن ← **Extract** ← فایل zip را پاک کنید.
3. Settings ← Show Hidden Files: فایل `.htaccess` باید در `public_html` باشد. بدون آن ریدایرکت‌ها و صفحه‌ی ۴۰۴ کار نمی‌کنند.

**با lftp (لینوکس، macOS یا WSL):** همان اسکریپت خودکار. رمز را با `read -s` بدهید تا در تاریخچه‌ی خط فرمان نماند:

```bash
npm ci && npm run build
read -s -p 'FTP password: ' LFTP_PASSWORD && export LFTP_PASSWORD
FTP_HOST=ftp.mahermana.com FTP_USER=deploy@mahermana.com FTP_DIR=. scripts/deploy-ftp.sh
```

**سرور مجازی:** `rsync -av --delete dist/ user@server:/var/www/mahermana/` و تنظیمات nginx در بخش ۵.

## ۵. میزبان‌های دیگر

**Netlify یا Cloudflare Pages:** مخزن را وصل کنید؛ Build command: `npm run build`، Publish (Output) directory: `dist`. نسخه‌ی Node از `.nvmrc` خوانده می‌شود. متغیرهای بخش ۲ را در تنظیمات همان سایت بنویسید. `_redirects` و `_headers` خودکار خوانده می‌شوند. این میزبان‌ها با هر تغییر در `main` خودشان می‌سازند؛ برای ساخت روزانه (مقاله‌های زمان‌بندی‌شده):

1. یک build hook بسازید: Netlify ← Site configuration ← Build & deploy ← Continuous deployment ← **Build hooks**؛ Cloudflare ← Workers & Pages ← پروژه ← Settings ← Builds ← **Deploy hooks**.
2. نشانی ساخته‌شده را در GitHub به‌عنوان Secret با نام `BUILD_HOOK_URL` بگذارید (هر کس این نشانی را داشته باشد می‌تواند ساخت راه بیندازد) و Variable `DEPLOY_TARGET` را `hook` کنید.

ورود به پنل مدیریت روی این میزبان‌ها: [cms-setup.md](cms-setup.md).

**nginx:** `root` را پوشه‌ی سایت بگذارید، `error_page 404 /404.html;` و `location / { try_files $uri $uri/ =404; }`. خروجی `npm run migrate:nginx` (ریدایرکت‌ها، فشرده‌سازی، کش یک‌ساله‌ی `/_astro/`، رفتن از http و www به نشانی اصلی) را داخل بلوک `server` بگذارید (`include`). برای فرم‌ها، فایل‌های `.php` را به PHP-FPM بدهید.

## ۶. فایل‌هایی که ساخت برای هاست می‌سازد

| فایل | برای | چه می‌کند |
|---|---|---|
| `.htaccess` | Apache و LiteSpeed | ریدایرکت‌های سایت قبلی، http به https و www به بدون www، صفحه‌ی ۴۰۴، فشرده‌سازی (Brotli یا gzip)، هدرهای امنیتی ساده، و «هر بار بپرس» برای صفحه‌ها تا تغییر فوراً دیده شود |
| `_astro/.htaccess` | Apache و LiteSpeed | کش یک‌ساله برای فایل‌هایی که نامشان با محتوایشان عوض می‌شود |
| `_redirects`، `_headers` | Netlify و Cloudflare Pages | همان ریدایرکت‌ها و هدرها |
| `api/form.php` | هاست PHP | گیرنده‌ی فرم‌ها، فقط وقتی `PUBLIC_FORM_ENDPOINT` روی همین سایت و `.php` است |

این فایل‌ها با هر ساخت از نو نوشته می‌شوند؛ دستی ویرایش نکنید. ریدایرکت تازه از پنل مدیریت ([migration.md](migration.md)). خود این فایل‌ها از بیرون خوانده نمی‌شوند (۴۰۴).

برای دیدن این‌که هاست فشرده‌سازی و کش را اجرا کرده است:

```bash
curl -s -o /dev/null -D - -H 'Accept-Encoding: br, gzip' https://mahermana.com/ | grep -iE 'content-encoding|cache-control|x-content-type'
```

باید `content-encoding: br` یا `gzip` و `cache-control: no-cache` ببینید. برای یکی از فایل‌های `/_astro/` (نامش را از سورس صفحه بردارید) `cache-control: public, max-age=31536000, immutable`.

## ۷. اگر چیزی درست کار نکرد

| نشانه | علت محتمل | راه‌حل |
|---|---|---|
| خطای ۵۰۰ در همه‌ی صفحه‌ها بعد از بارگذاری | هاست دستوری از `.htaccess` را اجازه نمی‌دهد | از هاست بخواهید `AllowOverride FileInfo` را برای سایت فعال کند؛ تا آن وقت `.htaccess` را موقتاً تغییر نام دهید |
| صفحه‌ی اصلی باز می‌شود ولی بقیه ۴۰۴ می‌دهند، یا نشانی‌ها `/dist/` دارند | پوشه‌ی اشتباه | `FTP_DIR` را درست کنید؛ محتوای `dist` باید مستقیم در `public_html` باشد |
| صفحه بدون ظاهر (فقط متن) | `_astro` بارگذاری نشده | دوباره بارگذاری کنید؛ در بارگذاری دستی فایل‌های پنهان را هم بفرستید |
| هنوز سایت وردپرس دیده می‌شود | فایل‌های وردپرس در `public_html` مانده، یا کش مرورگر | «روز اول»، مرحله‌ی ۲؛ صفحه را با Ctrl+Shift+R تازه کنید |
| `Login failed: 530` | نام کاربری یا رمز | نام کاربری کامل با `@دامنه`؛ رمز را در cPanel عوض و در Secret تازه کنید |
| `Certificate verification: … NOT trusted` یا `name mismatch` | گواهی FTP هاست برای نام سرور است، نه دامنه‌ی شما | `FTP_HOST` را همان نام سروری بگذارید که Configure FTP Client نشان می‌دهد؛ اگر نشد `FTP_VERIFY_CERTIFICATE` را `no` کنید |
| `max-retries exceeded` یا `Connection timed out` | هاست FTP از خارج را بسته | بخش ۳، «اگر GitHub به هاست وصل نشد» |
| گام آخر (بررسی سایت زنده) قرمز است | ریدایرکت یا صفحه‌ای درست کار نمی‌کند، یا دامنه هنوز به هاست تازه اشاره نمی‌کند | گزارش همان گام می‌گوید کدام نشانی؛ تا جابه‌جایی دامنه `DEPLOY_CHECK` را `off` کنید |
| مقاله‌ی زمان‌بندی‌شده منتشر نشد | اجرای روزانه خاموش شده | بخش ۳، «اجرای روزانه در مخزن عمومی» |
| فرم‌ها «ارسال نشد» می‌گویند | تنظیمات گیرنده | [forms-setup.md](forms-setup.md)، بخش رفع اشکال |
| `Node.js v… is not supported by Astro` هنگام ساخت | Node قدیمی‌تر از `.nvmrc` | Node `22.23.4` یا تازه‌تر نصب کنید (روی کامپیوتر خودتان با nvm: `nvm install`)؛ در Netlify یا Cloudflare، اگر متغیر `NODE_VERSION` گذاشته‌اید پاکش کنید تا `.nvmrc` خوانده شود |

## ۸. بررسی خودکار کیفیت

گردش کار `.github/workflows/quality.yml` (در Actions با نام **Quality check**) روی هر Pull Request، هر تغییر در `main`، هر شنبه صبح و با دکمه‌ی Run workflow اجرا می‌شود و این‌ها را می‌سنجد:

| گام | چه چیزی را می‌سنجد | روی کامپیوتر خودتان |
|---|---|---|
| Build | ساخته شدن سایت، از جمله درستی ریدایرکت‌ها و محتوای پنل | `npm run build` |
| Keyword map | عنوان، توضیح، H1 و عبارت اصلی هر صفحه مطابق [keyword-map.md](keyword-map.md)؛ دو صفحه بر سر یک عبارت رقابت نکنند | `npm run seo:keywords` |
| Map listing texts | متن‌های آماده‌ی نشان، بلد و گوگل‌مپ ([local-profiles.md](local-profiles.md)) طول درست و ادعای تأییدنشده نداشته باشند | `npm run local:profiles` |
| Every page in Chrome | همه‌ی صفحه‌ها، در عرض گوشی و کامپیوتر و با «کاهش حرکت»: قاعده‌های خودکار دسترس‌پذیری (axe، برای WCAG 2.2 تا سطح AA، شامل کنتراست رنگ‌ها و فرم‌ها بعد از ارسال خالی)، خطای مرورگر، فایل یا عکسی که بار نمی‌شود، پیوند شکسته یا پیوند به نشانی سایت قبلی، و بیرون‌زدن محتوا از صفحه‌ی گوشی | `npm run check:pages` (Chrome لازم دارد) |
| Lighthouse | پنج صفحه‌ی اصلی، هر کدام سه بار، با شبیه‌سازی گوشی و اینترنت کند: کارایی، بهترین روش‌ها و سئو دست‌کم ۹۰، دسترس‌پذیری دست‌کم ۹۵ | `npx @lhci/cli@0.16.1 autorun` |

**خواندن نتیجه:** تیک سبز یعنی هیچ‌کدام از این بررسی‌ها ایرادی پیدا نکرده است. بررسی خودکار همه‌ی مشکل‌های دسترس‌پذیری را نمی‌گیرد؛ بعد از تغییر بزرگ در طراحی، صفحه را یک بار فقط با صفحه‌کلید (Tab و Enter) هم امتحان کنید. اگر قرمز شد، روی اجرا و بعد روی گام قرمز بزنید؛ گزارش گام «Every page in Chrome» به فارسی می‌گوید کدام صفحه و کجای آن. گزارش کامل Lighthouse هر صفحه در بخش **Artifacts** همان اجراست (`lighthouse-reports`)؛ فایل zip را باز کنید و فایل‌های `.html` را در مرورگر ببینید.

**سرعت در یک نگاه:** هنگام تحویل، Lighthouse موبایل برای این پنج صفحه کارایی ۹۹ تا ۱۰۰ و برای دسترس‌پذیری، بهترین روش‌ها و سئو ۱۰۰ داد. چیزهایی که سرعت را پایین می‌آورند و در پنل مدیریت دست شماست: عکس خیلی بزرگ (بالای ۱۰ مگابایت بارگذاری نکنید؛ سایت خودش اندازه‌ها را می‌سازد)، و ویدیو یا کد بیرونی (مثل ویجت شبکه‌های اجتماعی) که در متن جاسازی شود.

## ۹. نقشه‌ی سایت و معرفی به گوگل

- نقشه‌ی سایت با هر ساخت به‌روز می‌شود: `https://mahermana.com/sitemap-index.xml`. صفحه‌های `noindex` (پنل مدیریت، صفحه‌های نظرخواهی، ۴۰۴، و فهرست اطلاعیه‌ها تا اولین اطلاعیه) در آن نیستند. مقاله‌ای که تاریخ انتشارش نرسیده یا پیش‌نویس است هم نیست.
- برای هر مقاله و اطلاعیه و دو صفحه‌ی فهرستشان، تاریخ آخرین تغییر (`lastmod`) از خود محتوا نوشته می‌شود: «تاریخ به‌روزرسانی» مقاله اگر پر شده باشد، وگرنه تاریخ انتشار. برای صفحه‌های دیگر تاریخی نوشته نمی‌شود، چون گوگل فقط به تاریخی اعتنا می‌کند که همیشه درست باشد. پس «تاریخ به‌روزرسانی» را فقط وقتی پر کنید که متن واقعاً تغییر کرده است.
- `robots.txt` به نقشه‌ی سایت اشاره می‌کند. «پینگ» کردن گوگل دیگر وجود ندارد؛ یک بار ثبت در سرچ کنسول کافی است و گوگل بعد از آن خودش سر می‌زند.
- ثبت در سرچ کنسول و Bing در روز راه‌اندازی: [migration.md](migration.md)، «روز راه‌اندازی». خلاصه: ویژگی از نوع **Domain** (تأیید با رکورد TXT در DNS)، Sitemaps ← `sitemap-index.xml` ← Submit، و در Bing Webmaster Tools گزینه‌ی Import از سرچ کنسول.
- بررسی ماهانه‌ی نقشه‌ی سایت و صفحه‌های ایندکس‌شده: [monthly-report.md](monthly-report.md).
