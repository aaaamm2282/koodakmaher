# انتقال از سایت قبلی بدون از دست دادن جایگاه در گوگل

سایت تازه روی همان دامنه `mahermana.com` می‌نشیند، ولی نشانی همه‌ی صفحه‌ها عوض می‌شود: نشانی‌های فارسی وردپرس (مثل `/درباره-ما/`) جای خود را به نشانی‌های کوتاه انگلیسی (مثل `/about/`) می‌دهند. گوگل نشانی‌های قدیمی را می‌شناسد و در نتایجش نشان می‌دهد. اگر این نشانی‌ها بعد از راه‌اندازی به صفحه‌ی «پیدا نشد» برسند، هم والدینی که از گوگل یا لینک‌های قدیمی می‌آیند گم می‌شوند و هم اعتباری که آن صفحه‌ها در گوگل داشتند از دست می‌رود.

راه‌حل، ریدایرکت ۳۰۱ است: هر نشانی قدیمی، بازدیدکننده و گوگل را به صفحه‌ی تازه‌ی همان موضوع می‌فرستد. راهنمای گوگل برای جابه‌جایی سایت سه نکته‌ی اصلی دارد: هر نشانی قدیمی به صفحه‌ی متناظرش برود، نه همه به صفحه‌ی اصلی؛ صفحه‌هایی که دیگر وجود ندارند کد ۴۰۴ یا ۴۱۰ بدهند؛ و ریدایرکت‌ها «دست‌کم یک سال» و بهتر است «تا هر وقت ممکن است» بمانند ([منبع](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)).

## آنچه آماده است

- **فهرست نشانی‌های قدیمی:** ۲۰ نشانی سایت قبلی که در نتایج گوگل پیدا شد (جست‌وجوی ۲۶ آبان ۱۴۰۵)، به‌اضافه‌ی نشانی صفحه‌ی کودکستان که خودتان فرستادید و صفحه‌ی «سلام دنیا» از گزارش سئو. فهرست کامل با تصمیم هر ردیف: [`docs/migration/old-urls.csv`](migration/old-urls.csv).
- **ریدایرکت‌ها برای هر نوع هاست:** از یک فهرست (`src/content/settings/redirects.json`) هنگام ساخت سایت، فایل `.htaccess` (برای Apache و LiteSpeed، یعنی بیشتر هاست‌های cPanel و DirectAdmin ایرانی) و `_redirects` (برای Netlify و Cloudflare Pages) ساخته می‌شود. برای nginx هم دستور جداگانه هست.
- **آزمایش واقعی:** همه‌ی ریدایرکت‌ها با نشانی‌های فارسی روی Apache 2.4.58 و nginx 1.24.0 واقعی آزمایش شد: ۷۶ مورد، بدون خطا. (Netlify و Cloudflare را بدون حساب نمی‌شود آزمود؛ بعد از راه‌اندازی، دستور بررسی را اجرا کنید.)
- **صفحه‌ی ۴۰۴ هوشمند:** اگر کسی با نشانی قدیمی‌ای بیاید که هنوز ریدایرکت ندارد، صفحه‌ی ۴۰۴ از کلمه‌های همان نشانی حدس می‌زند دنبال کدام صفحه بوده («شاید دنبال این صفحه بودید: دبستان مهارت‌محور») و پیوند واحدها، پیش‌ثبت‌نام و تماس را نشان می‌دهد.
- **جلوگیری از اشتباه:** اگر ریدایرکتی به صفحه‌ای برود که وجود ندارد، روی صفحه‌ی فعالی از سایت جدید بیفتد یا حلقه بسازد، ساخت سایت متوقف می‌شود و نسخه‌ی قبلی سایت سر جایش می‌ماند. ریدایرکت‌های زنجیره‌ای (الف به ب، ب به پ) خودکار یک‌مرحله‌ای می‌شوند.
- **ویرایش در پنل مدیریت:** «تنظیمات عمومی ← ریدایرکت‌ها (نشانی‌های سایت قبلی)».

## تصمیم‌هایی که با شماست

1. **فروشگاه** (`/shop/`، `/cart/`، `/my-account/`): سایت تازه فروشگاه ندارد. اگر فروشگاه جای دیگری ادامه پیدا می‌کند (مثلاً یک زیردامنه)، نشانی‌اش را بدهید تا این سه نشانی به همان‌جا بروند. اگر فروشگاه تعطیل است، کد ۴۱۰ می‌گیرند.
2. **ورود کارکنان** (`/ورود-کارکنان/`): اگر سامانه‌ی کارکنان جای دیگری هست، نشانی‌اش را بدهید.
3. **ورود والدین** (`/ورود-والدین/`): فعلاً به صفحه‌ی «برای والدین» می‌رود. اگر والدین با سامانه‌ای (مثلاً برای دیدن کارنامه یا گزارش) وارد می‌شوند، نشانی آن سامانه را بدهید.

تا وقتی تصمیم نگرفته‌اید، این نشانی‌ها صفحه‌ی ۴۰۴ هوشمند را نشان می‌دهند که برای گوگل درست است و هر وقت لازم شد قابل تغییر است.

## پیش از راه‌اندازی

1. **پشتیبان کامل از وردپرس** (فایل‌ها و پایگاه داده) از cPanel یا افزونه‌ی پشتیبان‌گیری بگیرید و نگه دارید. عکس‌های سایت قبلی (پوشه‌ی `wp-content/uploads`) هم در همین پشتیبان هست؛ هر کدام که رضایت‌نامه‌ی کتبی دارد، می‌تواند در سایت تازه استفاده شود.
2. **فهرست کامل نشانی‌های قدیمی را بیرون بکشید.** جست‌وجوی گوگل فقط بخشی از صفحه‌ها را نشان می‌دهد؛ فهرست کامل این‌جاهاست:
   - سرچ کنسول ← Performance (عملکرد) ← Search results ← بازه‌ی **۱۶ ماه** ← زبانه‌ی **Pages** ← دکمه‌ی **Export** ← فایل CSV (یا ZIP که داخلش `Pages.csv` است).
   - سرچ کنسول ← Indexing (فهرست‌سازی) ← Pages ← «View data about indexed pages» ← Export.
   - سرچ کنسول ← Links (پیوندها) ← «Top linked pages» در بخش پیوندهای بیرونی ← Export. این صفحه‌ها از سایت‌های دیگر لینک گرفته‌اند و مهم‌ترین‌ها هستند.
   - نقشه‌ی سایت قبلی، پیش از خاموش شدن وردپرس: `https://mahermana.com/sitemap_index.xml` یا `https://mahermana.com/wp-sitemap.xml`.
   - وردپرس ← ابزارها ← برون‌بری ← «همه‌ی محتوا» ← فایل XML.
   - نشانی‌هایی که روی بروشور، بنر، کارت ویزیت، کد QR، بیو اینستاگرام، تلگرام، ایتا یا واتساپ چاپ یا گذاشته شده‌اند.

   این فایل‌ها را بفرستید. هر کدام از این فایل‌ها با دستور زیر به فهرست اضافه می‌شود؛ برای هر نشانی تازه یک حدس اولیه زده می‌شود و بعد یکی‌یکی بازبینی می‌شود:

   ```bash
   npm run migrate:import -- ~/Downloads/Pages.csv ~/Downloads/export.xml https://mahermana.com/sitemap_index.xml
   npm run migrate:apply
   ```

3. **هاست را انتخاب کنید** و از جدول «هاست‌ها» در پایین همین راهنما ببینید کدام فایل کار می‌کند.
4. اگر سرور عوض می‌شود، یک روز پیش از جابه‌جایی TTL رکوردهای DNS را کم کنید (مثلاً ۳۰۰ ثانیه) تا تغییر زودتر به همه برسد.
5. **نسخه‌ی عادی را بسازید:** `npm run build`. نسخه‌هایی که با `SHOW_DRAFTS=1` یا `PREVIEW_PHOTOS=1` ساخته می‌شوند فقط برای بازبینی‌اند و همه‌ی صفحه‌هایشان `noindex` است؛ دستور بررسی زیر این اشتباه را پیدا می‌کند.

## روز راه‌اندازی

1. سایت را بارگذاری کنید ([deploy.md](deploy.md)؛ در انتشار خودکار، گام آخر همان بررسی مرحله‌ی ۲ را خودش انجام می‌دهد).
2. بررسی خودکار را اجرا کنید:

   ```bash
   npm run migrate:check -- https://mahermana.com --out docs/migration/check-1405-xx-xx.md
   ```

   این دستور همه‌ی نشانی‌های قدیمی (کد ۳۰۱ و مقصد درست، یا ۴۱۰ و ۴۰۴)، همه‌ی صفحه‌های نقشه‌ی سایت (کد ۲۰۰، بدون ریدایرکت، canonical درست، بدون `noindex`)، `robots.txt`، صفحه‌ی ۴۰۴ و یکی بودن نشانی سایت (http به https و www به بدون www) را می‌سنجد. باید «۰ خطا» بدهد. هشدار «اخبار noindex است» تا اولین اطلاعیه طبیعی است.
3. **سرچ کنسول:**
   - اگر ندارید، ویژگی (property) از نوع **Domain** بسازید؛ یک بار تأیید DNS، همه‌ی حالت‌های http و https و www را پوشش می‌دهد.
   - Sitemaps: نقشه‌ی قبلی (`sitemap_index.xml` یا `wp-sitemap.xml`) را حذف و `sitemap-index.xml` را اضافه کنید.
   - URL Inspection: برای صفحه‌ی اصلی، `/units/`، صفحه‌ی هر واحد، `/register/`، `/contact/` و `/about/` دکمه‌ی **Request indexing** را بزنید. گوگل برای این دکمه سقف روزانه دارد؛ اگر پیام سقف آمد، بقیه را فردا بزنید.
4. **Bing Webmaster Tools:** با گزینه‌ی Import، سایت را از سرچ کنسول بیاورید و نقشه‌ی سایت را ثبت کنید.
5. **لینک‌های بیرون از سایت را تازه کنید:** نشانی وب‌سایت در صفحه مراکز در نشان، بلد و گوگل‌مپ (لینک‌های آماده در `docs/local-profiles.md`)، بیو اینستاگرام، تلگرام، ایتا و واتساپ. کدهای QR قدیمی به لطف ریدایرکت‌ها کار می‌کنند، ولی در چاپ بعدی نشانی تازه را بگذارید.

## چه کارهایی نکنیم

- همه‌ی نشانی‌های قدیمی را به صفحه‌ی اصلی نفرستیم؛ گوگل صریحاً از آن منع کرده است.
- نشانی‌های قدیمی را در `robots.txt` نبندیم؛ گوگل باید آن‌ها را بخواند تا ریدایرکت را ببیند.
- برای صفحه‌های منتقل‌شده از ابزار Removals سرچ کنسول استفاده نکنیم؛ آن ابزار فقط پنهان می‌کند و این‌جا لازم نیست.
- ویژگی سرچ کنسول قبلی و داده‌هایش را پاک نکنیم.
- نشانی‌های تازه را به این زودی دوباره عوض نکنیم، و ریدایرکت‌ها را بعد از چند ماه برنداریم.

## افزودن ریدایرکت تازه

**از پنل مدیریت:** «تنظیمات عمومی ← ریدایرکت‌ها (نشانی‌های سایت قبلی)» ← افزودن. نشانی قدیمی را می‌شود کامل از نوار مرورگر کپی کرد (با `https://` یا به شکل `%D8…` هم قبول است). نوع «۳۰۱» برای صفحه‌ای که جای تازه دارد و «۴۱۰» برای صفحه‌ای که دیگر نیست. بعد از انتشار، سایت دوباره ساخته می‌شود؛ اگر مقصد اشتباه باشد، ساخت متوقف می‌شود و سایت فعلی دست نمی‌خورد.

**از فهرست:** در `docs/migration/old-urls.csv` ستون‌های `new_path` و `status` را پر کنید و `npm run migrate:apply` را اجرا کنید.

| ستون | معنی |
|---|---|
| `old_path` | نشانی قدیمی، با حروف فارسی |
| `old_title` | عنوان صفحه در سایت قبلی |
| `new_path` | صفحه‌ی تازه، مثل `/about/` |
| `status` | `301` منتقل شده، `410` حذف شده، `404` رها شود، `same` نشانی عوض نشده، خالی یعنی هنوز تصمیم نگرفته‌ایم |
| `guess` | از کجا آمده: `redirects.json`، یا حدس خودکار `strong` (نام واحد یا صفحه در نشانی هست) و `weak` (حدس کلی؛ حتماً بازبینی شود) |
| `clicks`، `impressions`، `links` | کلیک، نمایش و پیوند بیرونی از خروجی سرچ کنسول؛ پربازدیدها بالای فهرست‌اند |
| `source` | این نشانی از کدام فایل یا جست‌وجو آمده |

## هاست‌ها

| هاست | چه کاری لازم است |
|---|---|
| Apache یا LiteSpeed (cPanel، DirectAdmin و بیشتر هاست‌های اشتراکی ایرانی) | هیچ. فایل `.htaccess` همراه سایت بارگذاری می‌شود. فقط از دستورهایی استفاده شده که هر هاستی که ریدایرکت `.htaccess` را اجرا می‌کند اجازه می‌دهد؛ صفحه‌ی ۴۰۴ سایت (`ErrorDocument`)، رفتن از http به https و از www به نشانی بدون www هم در همان فایل است. اگر پوشه‌ی `dist` را با FTP بارگذاری می‌کنید، فایل‌های نقطه‌دار (`.htaccess`) را هم بفرستید؛ بعضی برنامه‌های FTP آن‌ها را پنهان می‌کنند. |
| Netlify یا Cloudflare Pages | هیچ. فایل `_redirects` خوانده می‌شود. Cloudflare در این فایل کد ۴۱۰ را نمی‌پذیرد، پس آن نشانی‌ها ۴۰۴ می‌دهند که برای گوگل فرقی ندارد. |
| nginx | خروجی `npm run migrate:nginx` را داخل بلوک `server` سایت بگذارید (`include`) و nginx را دوباره بارگذاری کنید. نمونه‌ی رفتن از http و www به نشانی اصلی هم ته همان خروجی هست. |
| هاستی که هیچ ریدایرکتی نمی‌پذیرد (مثل GitHub Pages) | با `STATIC_REDIRECT_PAGES=1 npm run build` بسازید: در هر نشانی قدیمی صفحه‌ای ساخته می‌شود که فوراً به صفحه‌ی تازه می‌رود. گوگل این نوع ریدایرکت (meta refresh فوری) را دائمی حساب می‌کند ([منبع](https://developers.google.com/search/docs/crawling-indexing/301-redirects))، ولی ریدایرکت سرور بهتر است. صفحه‌ی ۴۰۴ هم بازدیدکننده‌ی نشانی‌های قدیمی را به صفحه‌ی تازه می‌فرستد. |

## اگر دامنه هم عوض شود

اگر روزی سایت به دامنه‌ی دیگری برود (مثلاً یک دامنه‌ی `.ir`)، علاوه بر همه‌ی این‌ها: متغیر `SITE_URL` را هنگام ساخت عوض کنید، همه‌ی نشانی‌های دامنه‌ی قبلی را صفحه‌به‌صفحه به دامنه‌ی تازه ریدایرکت کنید و در سرچ کنسول از ابزار **Change of Address** استفاده کنید ([راهنمای گوگل](https://support.google.com/webmasters/answer/9370220)).
